VarMonLib — Real-Time PLC Variable Monitoring

Technology Proposal & Test Report · B&R Automation Platform · HP Indigo Digital Presses · Updated May 2026 — delta encoding production mode + cycle-time safety cap

1. Why We Need a New Communication Protocol

HP Indigo digital presses are built around B&R PLCs that manage the entire print engine — web handling, imaging, color path, exit, input, and dozens more subsystems. Each subsystem exposes hundreds to thousands of variables (commands, status flags, parameters, sensor readings), totaling ~90,000 addressable data points across the machine.

As the platform evolves, there is a growing set of technical requirements that demand high-performance, reliable, bidirectional data exchange between the PLC and external systems:

  • HMI & Operator Dashboards — Real-time visualization of machine state, live variable monitoring during print runs, and interactive write-back for parameter tuning — all requiring low-latency, high-frequency updates.
  • Device-to-Device Communication — Integration with external controllers, inspection systems, and peripheral equipment that need to exchange process variables at cycle-level timing without data loss.
  • Diagnostics & Service Tools — Field engineers need to observe specific subsystem variables in real-time, trace signal transitions, and verify that every state change is captured — not approximated by polling.
  • AI, Machine Learning & LLM Integration — Future use cases such as predictive maintenance, print quality optimization, and autonomous fault diagnosis require complete, gap-free data streams from the PLC. Machine learning models and large language models cannot learn from or reason about data that has holes — every variable update matters.
  • Data Recording & Analytics — Long-duration captures of hundreds of variables at full PLC cycle rate for offline analysis, trend detection, and process characterization.

The common requirement across all these use cases is a communication protocol that can stream large numbers of variables at PLC cycle rate with zero data loss, support bidirectional read/write, operate with minimal PLC CPU overhead, and scale from a handful of variables (targeted diagnostics) to thousands (full subsystem telemetry) — all through a single, unified interface. NanoPbLib
Embedded C library wrapping nanopb v0.4.9 — a zero-allocation Protocol Buffers encoder/decoder designed for microcontrollers. Encodes variable values directly from PLC memory addresses into compact binary packets. No dynamic memory, no heap, deterministic execution time. Includes npb_delta_compare & npb_shadow_build for change detection.
VarMonLib
Reusable function block (VM_Server) that manages the full TCP server lifecycle: connection accept, command parsing (subscribe, write, heartbeat, config), delta-encoded cyclic data streaming, and minimal-size keepalive packets when no values change. State machine: DISABLED → INIT → LISTEN → RUNNING → ERROR → CLOSING.
ProtoBufCom
Application-level glue task. Auto-generated init code registers all 89,440 variables from every subsystem (Exit, WHS, Input, BID, Drums, etc.) into a flat array. Each entry maps a var_id to its PLC memory address and data type (8 bytes/entry).
Python Gateway
FastAPI server that connects to the PLC, manages subscriptions, decodes protobuf updates in real-time, and serves a live web dashboard with REST API + WebSocket push. Includes a cycle-time-derived safety cap that prevents oversize subscriptions from triggering a PLC watchdog crash.

3. Wire Protocol

Communication uses Protocol Buffers (protobuf) — Google's language-neutral, platform-neutral binary serialization format. The schema (plcmonitor.proto) defines all message types:

// Variable update — sent from PLC every cycle (delta-encoded in production mode) message VarUpdatePacket { uint32 sequence = 1; // Packet sequence number (gap = lost packet) uint64 timestamp = 2; // PLC clock (microseconds) repeated VarValue values = 3; // Only the CHANGED variables (or empty for keepalive) } // Each variable value — tagged union, ~3 bytes for a BOOL, ~7 bytes for a REAL message VarValue { uint32 var_id = 1; oneof value { bool bool_val = 2; int32 int_val = 3; uint32 uint_val = 4; float real_val = 6; double lreal_val = 7; string string_val = 8; } } // Subscribe command — client tells PLC which variables to stream message SubscribeCommand { enum Action { SET = 0; ADD = 1; REMOVE = 2; } Action action = 1; repeated uint32 var_ids = 2; uint32 interval_ms = 3; } // All messages wrapped in PlcMessage envelope for TCP framing message PlcMessage { enum MsgType { VAR_UPDATE=0; SUBSCRIBE_CMD=1; HEARTBEAT=4; CONFIG_CMD=5; WRITE_VAR=7; ... } MsgType type = 1; oneof payload { VarUpdatePacket update=2; SubscribeCommand subscribe=3; ... } }

TCP framing: Every message is prefixed with a 4-byte little-endian length: [LENGTH:4B LE][PROTOBUF_BYTES:LENGTH]. This allows reliable message boundary detection over the TCP stream.

Why Protocol Buffers — Under the Hood

Protobuf encodes fields as compact tag + value pairs using varint (variable-length integer) compression — small numbers use fewer bytes. There is zero overhead for field names; only numeric tags travel on the wire.

VarValue { var_id = 42; bool_val = true; } Field 1 (var_id): tag = 0x08 value = 0x2A (42 as varint) Field 2 (bool_val): tag = 0x10 value = 0x01 (true) Total on wire: 4 bytes → 08 2A 10 01 Compare: JSON {"var_id":42,"bool_val":true} = 30 bytes (7.5× larger)

nanopb in C performs all this encoding directly into a pre-allocated buffer with zero heap allocation, single-pass, deterministic timing. This is what makes it safe to run inside a hard real-time PLC task class.

4. Delta Encoding & Keepalive — The Production Operating Mode Key Innovation

The defining performance feature of the system is that the PLC does not re-send values that haven't changed. This is what makes it possible to subscribe to thousands of variables while the on-the-wire bandwidth remains tied to the change rate, not the subscription size.

How it works

  • Each subscribed variable has an 8-byte shadow on the PLC, holding its last sent value.
  • Every cycle, npb_delta_compare performs a memcmp of every subscribed variable against its shadow. Only the changed ones are encoded into the outgoing packet. For each detected change, the shadow is atomically updated to the new value.
  • If no variable changed in this cycle, the PLC still emits a tiny keepalive packet (sequence + timestamp, zero values, ~14 bytes total). This guarantees a constant packet cadence — the gateway can always tell the PLC is alive and on schedule.
  • Every 100 cycles (≈ 640 ms at 6.4 ms cycle), the PLC forces a full snapshot of all subscribed values. This is a self-healing resync: any client that joined late or missed a packet gets the full state automatically.
  • Any subscription change (SET/ADD/REMOVE) invalidates the shadow, forcing the next packet to be a full snapshot of the new subscription.
Per-cycle send decision (TCP path): IF shadow_valid AND snapshot_count < 100 AND sub_count > 100 THEN changed = npb_delta_compare(...) IF changed > 0 THEN send delta packet with changed vars // e.g. 200 vars × ~7 B = ~1.4 KB ELSE send keepalive packet (0 vars) // ~14 B — fixed cadence guaranteed ELSE send full snapshot of ALL subscribed // initial sub or every 100 cycles rebuild shadow buffer END_IF

Why this matters in practice

On a real machine, even with 5,000 variables subscribed, only a few dozen are changing on any given cycle (counters, state machines, sensor readings). The other 4,950 are static values — control parameters, configuration flags, status bits that haven't flipped since startup. A traditional polling protocol re-sends all 5,000 on every poll. Delta encoding sends only the few dozen that actually changed.

The measured impact (test results below): a 4,500-var subscription at 6.4 ms cycle generates delta packets of just ~290 bytes on average — about 200× smaller than the equivalent full-snapshot (~64 KB) and well under the practical TCP send budget.

5. Variable Registry — Build & Update Workflow

The variable registry is the mapping between human-readable variable names (e.g., gExitCtrl.Output.Status.State) and their numeric IDs used on the wire. The registry is built automatically from the PLC source code and kept in sync between the PLC and Python sides:

1
Scan PLC Source
plc_var_scanner.py parses all .var and .typ files, resolves structs recursively to leaf fields
2
Generate JSON Registry
Outputs plc_var_registry.json — a flat map of var_id → {name, type} for all 89,440 variables
3
Generate PLC Init Code
plc_var_codegen.py emits Structured Text: VM_RegVar() calls that register each variable's memory address
4
Deploy & Verify
Same JSON loaded by Python gateway. Heartbeat carries registry count — mismatch detected automatically

AI-Assisted Registry Maintenance (Copilot Agent)

To ensure the registry stays correctly updated as developers modify PLC code, Vitaly Grosman has built a dedicated ProtobufScan agent for the S45 PLC AI Framework (GitHub Copilot). The agent can:

  • Automatically scan the PLC project for new, changed, or removed global variables
  • Regenerate the plc_var_registry.json and PLC init code with a single command
  • Detect registry mismatches between the PLC and Python sides
  • Guide developers through the correct update workflow — ensuring both sides stay in sync

Discovery — distinguishing real from phantom var_ids

Not every var_id in the registry necessarily has a real address on every PLC configuration. The Python gateway's discovery procedure (POST /api/plc/discover) probes the PLC in 500-var batches and records which IDs actually return data; the resulting available_vars set is what the test tools use as their candidate pool. On the test bed, discovery found 76,400 of 89,440 registry entries are wired to real PLC addresses.

⚠ Open Discussion: Maintenance Protocol
A formal registry maintenance protocol needs to be defined. Key questions: Who triggers a registry rescan after PLC variable changes? Should scan/codegen be part of CI/CD? How do we handle version rollouts across machines with different PLC software versions? Should the registry include a hash/checksum for stronger version verification beyond count?

7. Reliability & Stability Features New This Iteration

Three production-grade mechanisms were added during the May 2026 hardening pass to make the system safe to operate at scale and resilient against operator mistakes.

PLC ACK ordering (iTcpAckBusy) Fix
The PLC's iTcpSend function block is shared by all command responses (subscribe ACK, heartbeat, config response, write response). Previously, two consecutive commands could re-fire iTcpSend while the previous send was still in flight, corrupting the ACK stream. Now an iTcpAckBusy flag is polled every cycle and gates inbound command processing, so commands queue safely in the 64 KB RX buffer until the previous ACK fully completes.
Subscribe chunker delay Fix
Subscriptions larger than 5,000 vars are split into multiple SET/ADD chunks. The Python chunker now sleeps 50 ms before each non-first chunk (was incorrectly placed after), ensuring the PLC has time to consume one command and complete its ACK before the next arrives.
Cycle-time safety cap New
The Python gateway reads the PLC's actual cycle time from the CPU profiler vars and computes a safe subscription limit: safe = (cycle_ms / 6.4) × 10,000. The Subscribe and Full Test endpoints refuse oversize requests with a clear error explaining the watchdog risk; the UI auto-bounds its inputs. A force=true override is available for controlled testing.
Keepalive accounting (Python) Fix
The Python receive path now routes 0-var keepalive packets through the standard stats recorder so they're properly counted in packet rate, inter-packet timing, and benchmark integrity grades. Without this, a quiet machine would have shown a misleading low packet rate.

What these three rows tell us

1. Subscription size is decoupled from bandwidth. Going from 4,500 → 10,000 subs roughly doubles the changing-vars count (from 39.6 → 96.2/pkt) — but only because the larger pool happens to contain more naturally-changing IDs, not because we're paying for the idle ones. Bandwidth scales with change rate, not subscription size. Per the protocol design, a 50,000-sub subscription where only 200 vars are changing would generate the same ~290-byte packets as the 4,500-sub case.

2. Cycle time and subscription size trade off cleanly. Comparing 10K @ 6.4 ms vs 5K @ 3.2 ms, both deliver ≈ 15,000 var updates per second. The total throughput a given PLC can sustain is roughly constant; faster cycle gives better temporal resolution at the cost of subscription capacity.

3. PLC interval timing is rock-solid. The PLC's own cycle timestamps stay within ±1 ms of the configured cycle even during high-throughput tests. Any inter-packet jitter measured on the Python side is downstream (Windows TCP scheduling), not in the protocol itself.

What the Real Sim demonstrates

The Real Sim is the closest test we have to actual production use of the protocol — a diagnostic or HMI tool that holds a small set of "always-watched" variables open while the operator browses different subsystems and the watched-set rotates over time. It validates four things that no individual benchmark can:

  • Subscribe-stability under repeated SETs. Each of the 147 SET commands invalidates the PLC's delta shadow and forces a new initial snapshot of 1,235 vars, followed by deltas. Doing this 147 times back-to-back without losing a packet exercises every stability fix that went into this iteration (chunker timing, ACK ordering, snapshot sequencing).
  • Permanent-subscription steadiness. The 235 permanent vars (test cycle + CPU monitors) keep producing values throughout the churn — no gaps in their time series, no missed updates because of the subscription churn happening around them.
  • PLC headroom. 62% system idle and 0.15% task load with no overruns means the protocol is using a tiny fraction of available CPU even under aggressive churn. The PLC has plenty of room for its actual control logic.
  • End-to-end timing integrity. 3.205 ms PLC cycle interval (matches the configured TC#5) with σ = 0.42 ms over 93,912 packets — the protocol does not introduce timing drift.

Open Items & Roadmap

The system is production-grade for the realistic operational envelope (subscribe up to ~10,000 vars at 6.4 ms cycle, delta mode, 0 drops). The following items would lift the architectural ceiling further but are not blockers for current use cases:

Chunked initial snapshot (PLC change)
Spread the full-snapshot encode across multiple cycles (e.g., 2,000 vars per cycle) so even very large subscriptions can complete the initial sync without overrunning the cycle budget. Combined with the next item, this lets the system handle the full 50,000 architectural cap. ~80 lines of ST.
Spread npb_delta_compare across cycles (PLC change)
Scan only 1/N of the subscription each cycle. Trades change-detection latency (worst case N × cycle_ms) for steady-state CPU. Lets the system safely subscribe to 25,000+ vars at 6.4 ms cycle.
String value delta tracking
Currently npb_delta_compare skips entries with dataSize=0 (strings). Strings are sent only in the periodic full snapshot (~ every 640 ms). Making the comparison length-aware would give strings the same per-cycle responsiveness as numerics.
Registry hash / version handshake
Today's heartbeat compares registry counts (89,440). Adding a CRC32 of the plc_var_registry.json and exchanging it during connection setup would catch the rare case where two registries have the same count but different content.
