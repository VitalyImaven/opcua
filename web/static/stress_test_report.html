VarMonLib — Real-Time PLC Variable Monitoring

Technology Proposal & Stress Test Results · B&R Automation Platform · HP Indigo Digital Presses

1. Why We Need a New Communication Protocol

HP Indigo digital presses are built around B&R PLCs that manage the entire print engine — web handling, imaging, color path, exit, input, and dozens more subsystems. Each subsystem exposes hundreds to thousands of variables (commands, status flags, parameters, sensor readings), totaling ~90,000 addressable data points across the machine.

As the platform evolves, there is a growing set of technical requirements that demand high-performance, reliable, bidirectional data exchange between the PLC and external systems:

  • HMI & Operator Dashboards — Real-time visualization of machine state, live variable monitoring during print runs, and interactive write-back for parameter tuning — all requiring low-latency, high-frequency updates.
  • Device-to-Device Communication — Integration with external controllers, inspection systems, and peripheral equipment that need to exchange process variables at cycle-level timing without data loss.
  • Diagnostics & Service Tools — Field engineers need to observe specific subsystem variables in real-time, trace signal transitions, and verify that every state change is captured — not approximated by polling.
  • AI, Machine Learning & LLM Integration — Future use cases such as predictive maintenance, print quality optimization, and autonomous fault diagnosis require complete, gap-free data streams from the PLC. Machine learning models and large language models cannot learn from or reason about data that has holes — every variable update matters.
  • Data Recording & Analytics — Long-duration captures of hundreds of variables at full PLC cycle rate for offline analysis, trend detection, and process characterization.

The common requirement across all these use cases is a communication protocol that can stream large numbers of variables at PLC cycle rate with zero data loss, support bidirectional read/write, operate with minimal PLC CPU overhead, and scale from a handful of variables (targeted diagnostics) to tens of thousands (full machine telemetry) — all through a single, unified interface. 3. Wire Protocol

Communication uses Protocol Buffers (protobuf) — Google's language-neutral, platform-neutral binary serialization format. The schema (plcmonitor.proto) defines all message types:

// Variable update — sent from PLC every cycle for subscribed vars message VarUpdatePacket { uint32 sequence = 1; // Packet sequence number (gap = lost packet) uint64 timestamp = 2; // PLC clock (microseconds) repeated VarValue values = 3; // All subscribed variable values } // Each variable value — tagged union, ~3 bytes for a BOOL, ~7 bytes for a REAL message VarValue { uint32 var_id = 1; oneof value { bool bool_val = 2; int32 int_val = 3; uint32 uint_val = 4; float real_val = 6; double lreal_val = 7; string string_val = 8; } } // Subscribe command — client tells PLC which variables to stream message SubscribeCommand { enum Action { SET = 0; ADD = 1; REMOVE = 2; } Action action = 1; repeated uint32 var_ids = 2; uint32 interval_ms = 3; } // All messages wrapped in PlcMessage envelope for TCP framing message PlcMessage { enum MsgType { VAR_UPDATE=0; SUBSCRIBE_CMD=1; HEARTBEAT=4; CONFIG_CMD=5; WRITE_VAR=7; ... } MsgType type = 1; oneof payload { VarUpdatePacket update=2; SubscribeCommand subscribe=3; ... } }

TCP framing: Every message is prefixed with a 4-byte little-endian length: [LENGTH:4B LE][PROTOBUF_BYTES:LENGTH]. This allows reliable message boundary detection over the TCP stream.

Supported operations: Subscribe/unsubscribe variables, set transport mode (TCP/UDP), write variable values, heartbeat with registry count for sync verification, and continuous data streaming at PLC cycle rate.

How Protocol Buffers Work — Under the Hood

Protocol Buffers (protobuf) is a binary serialization format created by Google and used internally across virtually all their services. Unlike text-based formats (JSON, XML), protobuf encodes data into a compact binary stream with zero overhead for field names — only numeric field tags and values travel over the wire.

The encoding is built on two simple primitives:

1. VARINT encoding — variable-length integers Small numbers use fewer bytes. Each byte uses 7 data bits + 1 continuation bit. Value 1 → 0x01 (1 byte) Value 300 → 0xAC 0x02 (2 bytes) Value 89440 → 0x80 0xBA 0x05 (3 bytes) 2. Tag-Value pairs — each field is [tag][value] Tag = (field_number << 3) | wire_type Wire types: 0 = varint 1 = 64-bit 2 = length-delimited 5 = 32-bit

Here is a concrete example — how a single BOOL variable (var_id=42, value=true) encodes:

VarValue { var_id = 42; bool_val = true; } Field 1 (var_id, uint32): tag = 0x08 (field 1, wire type 0) value = 0x2A (42 as varint) Field 2 (bool_val, bool): tag = 0x10 (field 2, wire type 0) value = 0x01 (true) Total on wire: 4 bytes → 08 2A 10 01 Compare: JSON {"var_id":42,"bool_val":true} = 30 bytes (7.5× larger)

And a REAL (float) variable (var_id=1000, value=23.5):

VarValue { var_id = 1000; real_val = 23.5; } Field 1 (var_id): tag = 0x08 value = 0xE8 0x07 (1000 as varint, 2 bytes) Field 6 (real_val): tag = 0x35 value = 0x00 0x00 0xBC 0x41 (23.5 as IEEE 754 float) Total on wire: 8 bytes Compare: JSON {"var_id":1000,"real_val":23.5} = 31 bytes (3.9× larger)

For a packet with 5,000 subscribed variables, the encoding totals ~14,688 bytes (~2.9 bytes/var average). The same data in JSON would be ~120 KB — an 8× size difference that directly impacts throughput and latency.

Why This Is Ideal for Embedded / PLC Use

The key advantage for real-time PLC systems is how nanopb (the C implementation we use) performs the encoding:

  • Zero heap allocation — nanopb encodes directly into a pre-allocated static buffer. No malloc, no garbage collector, no memory fragmentation. The PLC's real-time guarantee is preserved.
  • Single-pass encoding — each variable is encoded in sequence by reading its value from the PLC memory address and writing the tag+value bytes. No intermediate data structures, no copies.
  • Deterministic timing — encoding time is proportional to the number of variables, with no branching or variability. This makes it safe to run in a hard real-time PLC task class.
  • Extremely low CPU load — encoding 5,000 variables into a 14 KB protobuf packet takes under 1 ms of PLC CPU time. Even at the fastest 3.2 ms cycle, the protobuf encoding consumes less than 5% of the available cycle time, leaving the vast majority of CPU capacity for the actual machine control logic. The PLC CPU profiler confirms that the ProtoBufCom task consistently runs well within its time budget with negligible impact on other tasks.
Encoding cost per cycle (measured): 209 vars → 234 bytes → < 0.1 ms encode time 1,000 vars → 1,881 bytes → ~ 0.2 ms encode time 5,000 vars → 14,688 bytes → ~ 0.8 ms encode time At 6.4 ms cycle: 0.8 ms / 6.4 ms = 12.5% CPU for 5,000 vars (worst case) At 20 ms cycle: 0.8 ms / 20 ms = 4% CPU for 5,000 vars Typical use (100–500 vars): < 1% CPU

4. Variable Registry — Build & Update Workflow

The variable registry is the mapping between human-readable variable names (e.g., gExitCtrl.Output.Status.State) and their numeric IDs used on the wire. The registry is built automatically from the PLC source code and kept in sync between the PLC and Python sides:

1
Scan PLC Source
plc_var_scanner.py parses all .var and .typ files, resolves structs recursively to leaf fields
2
Generate JSON Registry
Outputs plc_var_registry.json — a flat map of var_id → {name, type} for all 89,440 variables
3
Generate PLC Init Code
plc_var_codegen.py emits Structured Text: VM_RegVar() calls that register each variable's memory address
4
Deploy & Verify
Same JSON loaded by Python gateway. Heartbeat message carries registry count — mismatch detected automatically

When to update: Run the scanner + codegen whenever PLC global variables change (new subsystem, struct field added/removed, type changed). The JSON and generated ST files are committed to source control alongside the PLC project.

Proto schema changes: The .proto file only needs updating when adding a new message type (e.g., a new command). Variable additions/removals are handled entirely by the registry — no proto recompilation needed.

AI-Assisted Registry Maintenance (Copilot Agent)

To ensure the registry stays correctly updated as developers modify PLC code, Vitaly Grosman has built a dedicated ProtobufScan agent for the S45 PLC AI Framework (GitHub Copilot). The agent can:

  • Automatically scan the PLC project for new, changed, or removed global variables
  • Regenerate the plc_var_registry.json and PLC init code with a single command
  • Detect registry mismatches between the PLC and Python sides
  • Guide developers through the correct update workflow — ensuring both sides stay in sync

This means that even team members unfamiliar with the protocol internals can safely update the variable registry by simply asking the AI agent to scan and regenerate — reducing the risk of human error and keeping the protocol healthy over time.

Versioning & Sync Verification

The system includes built-in mechanisms to ensure all parties (PLC, Python gateway, consuming applications) are working with the same registry version:

  • Registry count in heartbeat — The PLC sends its RegistrySize in every heartbeat message. The Python gateway compares this to its local JSON entry count and flags a MISMATCH immediately if they differ.
  • Version tracking — The registry JSON and generated PLC code are committed together in source control, creating an auditable version history. The registry size (89,440) serves as a quick integrity fingerprint.
  • Health API — The /api/plc/health endpoint reports registry_in_sync: true/false, making it easy for any consuming application to verify it has the correct registry before processing data.
⚠ Open Discussion: Maintenance Protocol
A formal registry maintenance protocol needs to be defined — similar to what we have today for TPL updates. Key questions to resolve:
  • Who is responsible for triggering a registry rescan after PLC variable changes?
  • Should the scan/codegen be part of the CI/CD pipeline (automatic on every PLC build)?
  • How do we handle version rollouts across multiple machines with different PLC software versions?
  • Should the registry include a hash/checksum for stronger version verification beyond count?
  • What is the approval process before deploying a new registry version to production machines?

5. How External Applications Connect

Any application (AI framework, test tool, data recorder, custom dashboard) connects through the Python gateway's REST API or directly to the PLC's TCP socket:

Option A: Via Python Gateway (recommended) ─────────────────────────────────────────── Your App ──HTTP──▶ FastAPI :8082 ──TCP──▶ PLC :55000 │ │ ├─ GET /api/plc/vars → list all 89K variables ├─ POST /api/plc/subscribe → subscribe to var_ids [12, 45, 890] ├─ WS /ws/plc → real-time value push via WebSocket ├─ POST /api/plc/write → write a value to a PLC variable └─ GET /api/plc/health → connection state, sync status Option B: Direct protobuf (embedded/high-performance) ──────────────────────────────────────────────────── Your App ──TCP──▶ PLC :55000 │ ├─ Send PlcMessage(SUBSCRIBE_CMD) → subscribe to variables ├─ Recv PlcMessage(VAR_UPDATE) → binary protobuf stream └─ Send PlcMessage(WRITE_VAR) → write values

The gateway approach is preferred for most use cases — it handles connection management, reconnection, health monitoring, and provides a standard REST/WebSocket interface that any language or tool can consume without needing protobuf libraries.

Stress Test Results

TCP transport · B&R PLC · 3 cycle-time configurations · 209 → 89,440 variables

Test Objective & Results

Goal: Determine the maximum number of PLC variables that can be monitored in real-time via protobuf/TCP without losing a single update. "No loss" means that if a UDINT counter increments every PLC cycle, the receiving Python application sees every consecutive value — no gaps, no skipped numbers.

We ran a scaling stress test across three PLC task cycle times (3.2 ms, 6.4 ms, 20 ms), subscribing to progressively larger sets of variables — from 209 up to 89,440. For each configuration, the test measures packet rate, per-variable update rate, inter-packet timing, and most critically: data integrity — whether every value change is captured without gaps.

Beyond these limits, the B&R TCP socket buffer becomes the bottleneck: encoded packets exceed ~38 KB, and the NIC needs ~27 ms to flush them. When the send interval is shorter than the drain time, packets are silently skipped — the PLC simply cannot send faster than the hardware allows.

ⓘ Practical Note
In real production use, clients do not subscribe to the entire variable registry. The system is designed for on-demand monitoring: an operator or diagnostic tool subscribes only to the specific variables of interest at any given moment — typically tens to a few hundred. The full registry (~89K entries) serves as a lookup catalog; only actively subscribed variables consume bandwidth. This means even at the fastest 3.2 ms cycle time, the practical operating point (a few hundred variables) is well within the lossless zone with significant headroom.

Why Does Performance Plateau?

The bottleneck is the B&R AsTCP socket buffer drain rate, not the variable count or the protobuf encoder. The PLC's TcpSend function block can push ~38 KB into the kernel socket buffer, then returns ERR_FUB_BUSY until the NIC flushes the data. This flush takes ~27 ms regardless of payload size.

No, but send starts at next interval. At 20ms: send completes in ~19ms → just barely fits → 0% drops ⚠ 6.4ms interval: |=enc=|=send=|BUSY|BUSY|BUSY|=send=|BUSY|BUSY|BUSY|=send=| 27ms / 6.4ms ≈ 4.2 cycles → only 1 in 4 sends succeeds → 75% drops ✗ 3.2ms interval: |e|s|B|B|B|B|B|B|s|B|B|B|B|B|B|B|s| 27ms / 3.2ms ≈ 8.4 cycles → only 1 in 8 sends succeeds → 88% drops

Below the ceiling (small subscriptions), the encoded payload is small enough that TcpSend completes within a single cycle, so every cycle sends → max packet rate.

Above the ceiling (large subscriptions), the encoder outputs ~38–41 KB. Adding more vars doesn't increase the payload — the encoder simply packs what fits. So 10K, 20K, 50K, and 89K all produce identical packet sizes and throughput.
